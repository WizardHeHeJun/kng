# 异常与容错设计

> 可调用技能：分析功能在异常条件下的表现，生成异常流程和容错测试点。

## 触发条件

当策划案涉及以下场景时调用此技能：
- 网络操作（请求、下载、上传、同步）
- 服务端交互（API 调用、数据库操作）
- 外部依赖（第三方支付、推送、广告 SDK）
- 资源加载（图片、音频、配置文件）
- 定时任务或后台处理

## 输入

- 策划案中涉及的服务端交互和网络操作
- 功能依赖的外部系统清单
- 异常处理的已知规则（如策划案中提到的重试机制、提示语等）

## 执行步骤

1. **识别异常源**：列出功能涉及的所有可能失败的操作
   - 网络层：断网、弱网、超时、DNS 失败
   - 服务层：500 错误、服务不可用、响应超时
   - 数据层：数据格式错误、字段缺失、版本不兼容
   - 依赖层：第三方服务宕机、回调超时、证书过期
2. **分析异常影响**：每个异常源发生时，功能的表现
   - 用户看到什么（错误提示、loading、空白）
   - 数据状态（是否回滚、是否残留脏数据）
   - 恢复行为（自动重试、手动重试、需要重启）
3. **设计容错场景**：
   - 操作进行中断网 → 恢复后的处理
   - 重复请求 → 幂等性保证
   - 超时重试 → 重试策略和上限
   - 服务降级 → 降级方案和用户感知
4. **生成测试点**：每个异常场景生成一个测试点

## 输出规范

每个异常场景输出一个测试点，格式：
- `id`: TP-EX-xxx（EX = Exception）
- `type`: "exception"
- `title`: 异常描述（如"支付过程中断网后恢复"）
- `priority`: P0（涉及资产/支付）/ P1（核心功能异常）/ P2（展示类异常）
- `precondition`: 触发异常的前置条件
- `exception_type`: 异常类型（network/server/data/dependency）
- `expected`: 异常发生时的预期行为（提示、重试、回滚）

## 质量检查

- [ ] 每个网络操作至少覆盖：断网、弱网、超时三种异常
- [ ] 涉及资产变动的操作必须验证异常后的数据一致性
- [ ] 重试机制必须验证幂等性
- [ ] 标注了哪些异常可能导致用户资产损失
